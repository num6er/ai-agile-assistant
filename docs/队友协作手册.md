# 队友协作操作手册

> 这份手册写给本项目的第二位协作成员。跟着做一遍，即可完成环境搭建、跑通项目、并提交你的第一份代码。
> 仓库地址：https://github.com/num6er/ai-agile-assistant
> 协作规范见：[CONTRIBUTING.md](../CONTRIBUTING.md)

---

## 一、前置准备（一次性）

你需要在自己电脑上装好以下工具（都没装的话按顺序装）：

| 工具 | 用途 | 下载地址 |
|---|---|---|
| Git | 版本控制 | https://git-scm.com/downloads |
| Python 3.10+ | 运行后端 | https://www.python.org/downloads/（安装时勾选 Add to PATH）|
| Node.js LTS | 运行前端 | https://nodejs.org/ |
| GitHub 账号 | 提交代码 | https://github.com（注册邮箱要和后面 git config 的邮箱一致）|

装好后打开 PowerShell，依次确认：

```powershell
git --version        # 应输出 git version 2.x.x
python --version     # 应输出 Python 3.10 及以上
node --version       # 应输出 v20/v22 等 LTS 版本
```

## 二、接受协作者邀请

项目负责人（@num6er）会把你加成仓库协作者：

1. 去你 GitHub 注册邮箱收信，找到 GitHub 发来的邀请邮件
2. 点 **Accept invitation**
3. 或直接打开 https://github.com/num6er/ai-agile-assistant/invitations 点接受

接受后你才有推送代码的权限。

## 三、克隆仓库

选一个目录存放代码（比如 `D:\work`）：

```powershell
cd D:\work
git clone https://github.com/num6er/ai-agile-assistant.git
cd ai-agile-assistant
```

## 四、配置 Git 身份（重要）

这决定了你提交时显示的作者，必须用**你自己的 GitHub 账号绑定的邮箱**，否则 GitHub 上不会关联到你的头像和账号：

```powershell
git config user.name "你的姓名"
git config user.email "你的GitHub邮箱@xxx.com"
```

> 这里用的是仓库本地配置，只影响这个项目，不会改你电脑的全局设置。

验证：

```powershell
git config user.name
git config user.email
```

## 五、搭建后端环境

```powershell
cd backend

# 1. 创建虚拟环境
python -m venv .venv

# 2. 激活虚拟环境
.venv\Scripts\Activate.ps1
# 如果提示"无法加载...因为在此系统上禁止运行脚本"，先执行一次：
#   Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
# 然后重新激活

# 3. 安装依赖
pip install -r requirements.txt

# 4. 复制 .env 模板并填入你自己的 API Key
Copy-Item .env.example .env
notepad .env
```

打开的 `.env` 里找到这三行，填成你自己的（去 https://platform.deepseek.com 注册，新用户送免费额度）：

```
LLM_API_KEY=你自己的sk-xxx
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

> ⚠️ **`.env` 绝对不要提交到 git！** `.gitignore` 已经忽略了它，但不要用 `git add -f` 强制添加。

## 六、搭建前端环境

**新开一个 PowerShell 窗口**（后端那个别关）：

第一次安装要等 1~2 分钟。

## 八、标准开发流程

每次干活都按这个流程来：

```bash
# 1. 先切到 main 并拉取最新代码
git checkout main
git pull origin main

# 2. 从 main 建自己的功能分支（按 CONTRIBUTING.md 的命名规范）
git checkout -b feature/你要做的功能

# 3. 改代码

# 4. 改完后只 add 你动过的文件（不要 git add . 全选，避免误提交 .env）
git add <你改的文件路径>
git commit -m "feat: 具体做了什么"   # 提交信息按规范写

# 5. 推送到远程
git push origin feature/你要做的功能
```

然后去 GitHub 仓库页面，顶部会出现黄色提示条 **Compare & pull request**，点进去：

- 标题写清楚这个 PR 做了什么
- 描述会自动带出 PR 模板，按模板填
- 点 **Create pull request**
- 通知负责人 Review，他确认后点 **Merge pull request** 合入 main

合并完成后，在本地更新：

```bash
git checkout main
git pull origin main
```

## 九、提交信息速查

格式：`<类型>: <说明>`，详见 [CONTRIBUTING.md](../CONTRIBUTING.md)

| 类型 | 何时用 | 示例 |
|---|---|---|
| `feat` | 加功能 | `feat: 任务看板增加按状态筛选` |
| `fix` | 修 bug | `fix: 修复空 PRD 时页面报错` |
| `docs` | 文档 | `docs: 补充 Docker 部署步骤` |
| `test` | 加测试 | `test: 增加故事拆解接口测试` |
| `refactor` | 重构 | `refactor: 抽取 LLM 调用重试逻辑` |
| `chore` | 杂项 | `chore: 更新依赖版本` |

❌ 不要写：`update`、`修改`、`111`、`asdf`。

## 十、建议的入门任务（任选其一，做完走一次完整 PR 流程）

这些是真实可做的小任务，做完都能合入：

1. **文档类**：在 `README.md` 补充「常见问题 FAQ」章节（比如端口被占用怎么办、npm install 失败怎么处理）
2. **文档类**：在 `docs/` 下新建「Docker 部署验证记录.md」，按 `docker-compose.yml` 实测一遍并记录结果
3. **前端类**：给 `frontend/src/views/ProjectDetail.vue` 的任务看板表格增加一个「按状态筛选」的下拉框
4. **前端类**：把页面上残留的英文按钮（如 "Back"、"New Project"）改成中文
5. **后端类**：在 `backend/tests/` 下补充 1~2 个接口的单元测试用例（参考已有测试写法）
6. **后端类**：给 `backend/app/llm/client.py` 的 LLM 调用加一个失败重试机制（重试 2 次）

> 任务先和负责人确认一下分工，避免两人改到同一处冲突。

## 十一、注意事项

1. **不要提交 `.env`**：里面有 API Key，泄露会被盗刷。改完代码用 `git status` 看一眼，确认没有 `.env` 被暂存。
2. **不要提交 `node_modules/`、`.venv/`、`instance/`、`dist/`**：这些是依赖或运行产物，仓库里不该有。
3. **改完先自测**：后端跑 `pytest`，前端本地启动看效果，没问题再提 PR。
4. **遇到接口/数据结构改动**：先和负责人同步，避免前后端对不上。
5. **有问题直接在群里问**，不要自己闷头改一晚上最后冲突。

## 十二、遇到问题

- Git 命令报错：先复制完整报错信息发给负责人
- 依赖装不上：截图报错 + 说明是 Python 还是 Node 的
- 接口调不通：先确认后端在跑、`.env` 里 API Key 正确、账户有余额
- LLM 报错：看后端终端输出的具体错误信息
